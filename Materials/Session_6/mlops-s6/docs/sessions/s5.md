# Session 5 · Kubernetes and load: lab guide

Goal: run the fraud API on a local kind cluster, measure its P95 latency and throughput at 1 and 3 replicas, decompose the 200 ms budget, and estimate the cost per 1,000 predictions.

Deliverable: a half-page report with P95 and throughput at 1 and 3 replicas, the main latency item, and the estimated cost per 1,000 predictions.

## 0. Prerequisites

- Docker running, plus `kind`, `kubectl` and `locust` (installed with the project).
- Run `make pipeline` once, so that the golden split exists: the load test draws its payloads from it.

## 1. Build and deploy v1

```bash
make kind-up                       # kind create cluster --name mlops --config k8s/kind-config.yaml
docker build -t fraud-api:v1 .
make kind-deploy VERSION=v1        # kind load + kubectl apply deployment.yaml, service.yaml
kubectl get deployments,pods,services
curl http://localhost:8080/health  # the API answers through the kind port mapping
```

The Deployment starts with 3 replicas (`k8s/deployment.yaml`). Keep that as the starting point, then change the count with `kubectl scale`.

## 2. Load test protocol

Use the same load profile for every run, or the comparison means nothing. The profile is set in the command, not in the Locust UI.

```bash
locust -f loadtest/locustfile.py --host http://localhost:8080 \
       --headless -u 50 -r 10 -t 1m --csv reports/load_k8s_<N>r
```

Replace `<N>` with the number of replicas (`1r`, `3r`). The command writes `reports/load_k8s_<N>r_stats.csv`. In that file, read:

- the `95%` column: P95 in milliseconds, for the row `/predict` (the aggregated row is `Aggregated`);
- the `Requests/s` column: throughput.

Protocol for each run:

1. Set the replica count: `kubectl scale deploy/fraud-api-v1 --replicas=<N>`, then `kubectl rollout status deploy/fraud-api-v1`.
2. Wait about 30 seconds so that the pods are ready and the caches are warm.
3. Run the load test, once with 1 replica and once with 3.
4. Note the throughput of the aggregated row. Use the throughput at the same load profile for both runs.

Caveat: on a laptop, Locust, kind and the API share the same CPU. Close heavy applications, and mention this in the report.

To locate the saturation point, you can rerun with `-u 100` or `-u 150` and check where the P95 starts to climb.

## 3. Decompose the latency budget

The budget table (slide 25) has four spans. The table below says how to fill each row. The values are approximate: the P95 of each span does not add up exactly to the total.

| Span | How to measure it |
| --- | --- |
| Total end-to-end P95 | Locust `95%` column, `/predict` row. This is the figure to compare with 200 ms. |
| Network and port mapping | Client P95 minus server P95 (below). |
| Server-side P95 | Histogram `api_request_duration_seconds` on `/metrics`, endpoint `/predict`. |
| Model inference | Field `inference_ms` in the prediction log events (one per request). |
| Validation, serialisation, logging | Server P95 minus the inference part, as a residual. |

Server-side P95 from the histogram:

```bash
curl -s http://localhost:8080/metrics | grep api_request_duration_seconds
```

The buckets are coarse around 200 ms (0.1, 0.2, 0.3 s), so the quantile is interpolated. Give it as an order of magnitude. For a cleaner value, use Prometheus with `histogram_quantile(0.95, sum by (le) (rate(api_request_duration_seconds_bucket{endpoint="/predict"}[1m])))`, the same expression as the alert `LatencyP95High`.

Inference time: each prediction logs `inference_ms`, which covers feature assembly, `predict_proba` and the metric updates. Locally the events go to `logs/predictions.jsonl`. Inside the cluster, check where the logs go before relying on them (`kubectl logs deploy/fraud-api-v1`), and read the P50/P95 of `inference_ms` from the log file.

Read the result this way: if inference dominates the server time, optimise the model or its preprocessing. If the residual dominates, look at validation, JSON handling and the number of workers. If the gap between client and server dominates, the cause is outside the pod (port mapping, Locust itself).

## 4. Cost per 1,000 predictions

On kind the infrastructure is free, so the cost is an assumption. Set an hourly price for the instance that would run one replica, and state it in the report, for example `C_h = X EUR/hour per replica` (choose the value yourself and justify it: the vCPU and memory requests in `deployment.yaml` are 100m and 256Mi, with limits of 500m and 512Mi).

Use the throughput at saturation, not the offered load:

```
cost per 1,000 predictions = (C_h × replicas × 1000) / (throughput_rps × 3600)
```

Example with made-up numbers, to show the calculation only: C_h = 0.05 EUR per replica-hour, 3 replicas, 120 requests/s at saturation gives 0.05 × 3 × 1000 / (120 × 3600) ≈ 0.00035 EUR, that is about 0.035 cent per 1,000 predictions. Replace these numbers with your own measurements.

Report the cost for both the 1-replica and the 3-replica runs. The difference shows whether scaling out is efficient.

## 5. What to write in the half-page report

- Setup: machine, Docker resources, kind version, load profile (`-u`, `-r`, `-t`).
- A table with the 1-replica and 3-replica runs: P95 end-to-end, server P95, throughput, error rate.
- The budget breakdown for the 3-replica run, with the main latency item named explicitly.
- The cost per 1,000 predictions, with the hourly price assumption stated.
- One sentence on the limit of the experiment (single laptop, shared CPU) and one on the next step.
