# Session 7 · Drift and retraining: lab guide

Goal: measure drift on the fraud API's traffic with K-S, chi-squared and PSI, tell which drift type each test can see, and wire a drift verdict to a retraining run in GitHub Actions, only after you have diagnosed the cause.

Each step is small and ends with a **Check**. Do not skip ahead.

Parts 9 and 10 are optional. Part 9 (the PSI by hand) suits anyone who wants to understand the verdict before trusting it. Part 10 (GitLab CI) suits groups who finished Parts 0 to 6 with time left. Both can be done after the deliverable.

Deliverable: a drift-triggered retraining run visible in GitHub Actions, the drift reports of the baseline, data-drift and concept-drift runs, and a paragraph on what the retraining changed and what it did not (step 6).

Terminals: **terminal A** runs the API and stays open. **Terminal B** runs the commands of this guide.

## Part 5 · Wire the trigger (only after the diagnosis)

The exit code of `fraud.drift` is the trigger: `3` when the max PSI is above `psi_retrain` (0.25 in `params.yaml`), `0` otherwise. The trigger starts a retraining run only on `3`, and only after your diagnosis of step 4.

**5.1** Save this script as `retrain_on_drift.sh` at the root of the repository:

```bash
CURRENT=${CURRENT:-logs/drift.jsonl}
uv run python -m fraud.drift --current "$CURRENT"
code=$?
if [ "$code" -eq 3 ]; then
  psi=$(uv run python -c 'import json; print(round(json.load(open("reports/drift.json"))["max_psi"], 3))')
  gh workflow run train.yml -f reason="drift PSI $psi"
fi
```

**Check:** `bash -n retrain_on_drift.sh` prints nothing (no syntax error).

**5.2** Check that the trigger stays silent on normal traffic. Run it on the baseline:

```bash
CURRENT=logs/baseline.jsonl bash retrain_on_drift.sh
```

**Check:** the output ends with `-> ok`, and no workflow starts.

**5.3** Run the trigger on the data-drift log (the step 2 traffic, saved in `logs/drift.jsonl`):

```bash
bash retrain_on_drift.sh
```

**Check:** the output says `reason=drift PSI` followed by a value above 1, and `gh` prints that a workflow run was created.

**5.4** Watch the run:

```bash
gh run list --workflow train.yml --limit 3
gh run watch
```

**Check:** the run goes through the data, training, evaluation gate and export steps. The `publish` job then waits for approval in the `production` environment. Approve it, or leave it waiting and say so in your report.

**Note:** the `|| gh workflow run` form is not used on purpose. Chaining with `||` would start a training run on any failure of the drift command, not only on a drift verdict.

## Part 9 · Optional: read the PSI by hand

Use this part to understand the number that drives `retrain`, before you trust it. Do it on paper or in a scratch file, not in the repository. It needs no API and no GitHub.

**9.1** Compute the PSI of a feature split into four bins. The reference has equal bins, `[0.25, 0.25, 0.25, 0.25]`. Today's traffic has `[0.10, 0.20, 0.30, 0.40]`. For each bin, compute `(current - reference) * ln(current / reference)`, then add the four terms.

**Check:** the PSI is about `0.23`. That is above `psi_alert` (0.1) and below `psi_retrain` (0.25): an alert, not a retraining.

**9.2** Swap the two distributions: the reference becomes `[0.10, 0.20, 0.30, 0.40]` and the current becomes `[0.25, 0.25, 0.25, 0.25]`. Compute the PSI again.

**Check:** you get the same value. For fixed bins the formula is symmetric. The code is not quite symmetric, because `psi()` takes its bin edges from the reference: swapping the roles also moves the bins.

**9.3** Test the number of bins. Save this in a scratch file and run it with `uv run python` in the repository:

```python
import numpy as np
from fraud.drift import psi

ref = np.random.default_rng(0).normal(0, 1, 10_000)
cur = np.random.default_rng(1).normal(0.5, 1, 10_000)
for bins in (5, 10, 20):
    print(bins, round(psi(ref, cur, bins=bins), 3))
```

**Check:** the output is `5 0.203`, `10 0.224`, `20 0.233`. The verdict is stable here, but the value moves with the bins: this is why the thresholds are rules of thumb (see the last limit of this guide).

**9.4** Measure the noise. Draw 200 pairs of samples of 500 points from the same distribution, then compute the PSI of each pair:

```python
import numpy as np
from fraud.drift import psi

vals = [psi(np.random.default_rng(i).normal(0, 1, 20_000),
            np.random.default_rng(100 + i).normal(0, 1, 500)) for i in range(200)]
print("median", round(np.median(vals), 3), "max", round(max(vals), 3))
```

**Check:** the maximum is below `0.05`. With 500 requests and no drift at all, a PSI of 0.1 would almost never appear: the alert threshold is safe for this sample size. With 50 requests it would not be.

**9.5** Compare K-S and PSI on a small shift. The reference is the standard normal distribution with 10 000 points. The current traffic is the same distribution shifted by `0.1` standard deviation, also 10 000 points. Compute the K-S test (`scipy.stats.ks_2samp`) and the PSI.

**Check:** the K-S p-value is far below 0.01 (about `4e-7`), so K-S says the change is real. The PSI is about `0.007`, far below 0.1, so PSI says the change is negligible. Both are right: the sample is large enough to see a tiny shift, and the shift is too small to matter. Write one sentence on which of the two you would alert on, and why.

## Part 10 · Optional: the retraining mechanism in GitLab CI

This part repeats the drift-to-retraining wiring of Part 5, in GitLab CI instead of GitHub Actions. Do it in your own GitLab project (gitlab.com or your group's instance), with a copy of the repository. Check the YAML with the pipeline editor (*Build > Pipeline editor*, then *Validate*) before every run.

**10.1** Create the GitLab project, push the repository, and add the Kaggle token as a CI/CD variable (*Settings > CI/CD > Variables*, `KAGGLE_API_TOKEN`, masked).

**Check:** the variable is listed with a masked value, and the project has a `main` branch.

**10.2** Create `.gitlab-ci.yml` with the drift job only. Replace the `TODO` lines with your own choice of trigger.

```yaml
stages: [drift, retrain, publish]

default:
  image: python:3.12
  before_script:
    - pip install uv
    - uv sync --locked

drift:
  stage: drift
  rules:
    - if: $CI_PIPELINE_SOURCE == "trigger" || $CI_PIPELINE_SOURCE == "schedule" || $CI_PIPELINE_SOURCE == "web"
  script:
    - |
      set +e
      uv run --no-sync python -m fraud.drift --current "${CURRENT:-logs/drift.jsonl}"
      code=$?
      set -e
      if [ "$code" -eq 3 ]; then echo "RETRAIN=true" > retrain.env
      elif [ "$code" -eq 0 ]; then echo "RETRAIN=false" > retrain.env
      else exit "$code"; fi
  artifacts:
    reports:
      dotenv: retrain.env
    paths:
      - reports/
```

Run it from *Build > Pipelines > Run pipeline*, with the variable `CURRENT` set to `logs/baseline.jsonl`. The lab repository must contain these logs: commit them for this exercise. In production, the job would fetch the logs from storage instead.

**Check:** the job log ends with `-> ok`, and the job artifacts contain `retrain.env` with `RETRAIN=false`.

**10.3** Add the `retrain` job. It must run only after a drift verdict, and it reads the verdict from the dotenv file of the `drift` job.

```yaml
retrain:
  stage: retrain
  needs:
    - job: drift
      artifacts: true
  resource_group: train
  script:
    - |
      if [ "$RETRAIN" != "true" ]; then echo "no drift verdict: nothing to retrain"; exit 0; fi
    - uv run --no-sync python -m fraud.data
    - uv run --no-sync python -m fraud.train
    - uv run --no-sync python -m fraud.evaluate
    - uv run --no-sync python -m fraud.export_model
  artifacts:
    paths:
      - model/
      - reports/
```

**Check:** with `CURRENT=logs/baseline.jsonl`, the `retrain` job prints `nothing to retrain`. With `CURRENT=logs/drift.jsonl`, it runs the four steps, and the evaluation gate prints a pass or a fail in the job log.

**Note:** the condition is a shell `if` inside the job, not a `rules:` clause. A `rules:` clause is evaluated when the pipeline is created, before the drift job has written the dotenv file.

**10.4** Add the `publish` job. It must come after the gate and wait for a human.

```yaml
publish:
  stage: publish
  needs:
    - job: drift
      artifacts: true
    - retrain
  when: manual
  allow_failure: false
  environment: production
  script:
    - echo "build and push the image from model/, as in train.yml"
```

**Check:** the `publish` job waits for a click (*Play*) and does not run by itself. Click it on the baseline pipeline (`RETRAIN=false`). The skeleton has no guard yet, so it publishes whatever the pipeline produced: add the same test as `retrain` (`RETRAIN` must be `true`, otherwise exit 0 with a message), then check that the baseline run now refuses to publish.

**Note:** `when: manual` is the approval, the equivalent of the `production` environment with required reviewers in GitHub. Protected environments with approval rules are a separate GitLab feature, not needed here.

**10.5** Trigger the pipeline from outside, as the drift monitor would. Create a pipeline trigger token (*Settings > CI/CD > Pipeline trigger tokens*) and call the API with the drift log:

```bash
curl --request POST \
  --form token="$TRIGGER_TOKEN" \
  --form ref=main \
  --form "variables[CURRENT]=logs/drift.jsonl" \
  "https://gitlab.com/api/v4/projects/<PROJECT_ID>/trigger/pipeline"
```

**Check:** the response contains `"source": "trigger"`, and the pipeline runs the four stages through to the manual `publish` job. Keep the token out of the repository.

**10.6** Map the GitHub concepts to their GitLab equivalents, from what you built:

- `workflow_dispatch` with an input `reason` corresponds to a trigger or a manual run with a variable.
- `needs` with `GITHUB_STEP_SUMMARY` corresponds to dotenv artifacts and the job log.
- `environment: production` with required reviewers corresponds to `when: manual` in this lab.
- `concurrency` corresponds to `resource_group`.

**Check:** you can say in one sentence which of these four concepts is the weakest in the lab, and what you would add to make it stronger in a real company.

**10.7** Answer the question the lab keeps for last. In production, where does the drift job read the logs from, and which role can read them? The runner must reach that location: name the access you would give the runner, and say why you would not put the logs in the repository.

## Known limits of this lab

These limits are part of the lesson. Name them in your report.

- **Same data, same model.** The CI retraining reproduces the pipeline on the same training split, so the model comes out identical. The pipeline is proven; nothing has adapted to the drift.
- **Two registries.** The CI workflow runs MLflow with a local SQLite database on the GitHub runner (`MLFLOW_TRACKING_URI=sqlite:///mlflow.db`). The run and the `@staging` alias live on the runner, not in your local MLflow at http://localhost:5000. Evidence is the Actions summary and the `model` and `reports` artifacts.
- **The exit code says drift, not cause.** A unit bug gives the same exit code 3 (Part 4). The trigger is only as good as the diagnosis that precedes it.
- **The reference is a choice.** The reference is a healthy production window, and the training split would give a different verdict (Part 7). Choosing the reference is a decision you must state.
- **Thresholds.** `psi_alert` (0.1) and `psi_retrain` (0.25) are rules of thumb, not validated on real data. State how sensitive your verdict is to the number of bins.
