# Session 6 · Four-layer monitoring: lab guide

Goal: watch the fraud API across the four monitoring layers in Grafana, provoke two incidents, make the matching alerts fire in Prometheus, and respond with the runbook.

Each step is small and ends with a **Check**: if the check fails, fix it before going on. Do not skip ahead, the next steps assume the previous ones.

Deliverable: a Grafana screenshot of the baseline and of each incident, a short report for each incident (alert, runbook section, diagnosis, decision and recovery times) and the calibrated threshold table (step 5).

Terminals: you need **three**. Terminal A runs the API and stays open. Terminal B runs the commands of this guide. Terminal C is free for checks.

---

## Part 0 · Setup

**0.1** Install the Python environment:

```bash
make setup
```

**Check:** the command ends without error and `uv run python -c "import fraud; print('ok')"` prints `ok`.

**0.2** Run the tests:

```bash
make test
```

**Check:** the last line says `passed`, with no `failed`.

**0.3** Start Prometheus and Grafana (Docker needed):

```bash
make monitoring
```

**Check:** `docker compose ps` shows `prometheus` and `grafana` as `running`.

**0.4** Open http://localhost:9090 (Prometheus) and http://localhost:3000 (Grafana, login `admin` / `admin`).

**Check:** both pages load. Prometheus is the database and the alert engine; Grafana only draws.

## Part 1 · Expose the API to Prometheus

**1.1** In terminal A, start the API with the lab threshold:

```bash
DECISION_THRESHOLD=0.005 make api
```

The model exported with the course carries a decision threshold of 0.0007, which flags almost every transaction (99 %). The lab uses 0.005 instead, so that the baseline flags about 2 % of transactions, like the frauds of the simulated traffic. Do not change the model: this is one of the things you would raise in a real review.

**Check:** the log shows `Application startup complete`.

**1.2** In terminal B:

```bash
curl -s localhost:8000/health
```

**Check:** the answer contains `"status": "ok"`. If it says `"degraded"`, the model is not loaded: read the startup log of terminal A.

**1.3** Send one transaction through the simulator:

```bash
uv run python -m fraud.simulate --n 1
```

**Check:** it prints `1 requests sent to http://localhost:8000, 0 errors`.

**1.4** Read the raw metrics:

```bash
curl -s localhost:8000/metrics/ | grep '^api_requests_total'
```

**Check:** one line for `endpoint="/predict"` with `status="200"`, value `1.0`.

**1.5** Open http://localhost:9090/targets.

**Check:** the `fraud-api` target with `env="host"` is `UP`. The `env="kind"` target is `DOWN`: this is expected in this session.

**1.6** In Prometheus (http://localhost:9090/graph), run the query `api_requests_total`.

**Check:** the graph lists the same series as step 1.4. This is the same data, stored by Prometheus.

## Part 2 · Baseline with normal traffic

**2.1** Send 500 normal requests:

```bash
make simulate
```

**Check:** the output says `500 requests sent`, with `0 errors`.

**2.2** In Grafana, open the dashboard **Fraud API · 4-layer monitoring**. Read row 1, **Infrastructure**: the P50 and P95 of `/predict`, and the throughput by status.

**Check:** P95 is well under 200 ms. Write the value down: it is your baseline for latency.

**2.3** Read row 2, **Input distribution**: the median incoming amount.

**Check:** the value is between 10 and 25 EUR. Write it down.

**2.4** Read row 3, **Prediction distribution**: the share of transactions flagged.

**Check:** it is close to the 2 % of frauds in the traffic. Write it down.

**2.5** Read row 4, **Business outcome**: recall and precision over 15 minutes.

**Check:** the panels show values, not "No data". Labels come back for about 30 % of the transactions, so the numbers are noisy: that is expected.

**2.6** Check that no clear customer id reaches the logs:

```bash
grep -c '"customer_id"' logs/predictions.jsonl
```

**Check:** the answer is `0`. The field is called `customer_hash`, not `customer_id`.

## Part 3 · Incident 1: the API is slow

**3.1** Read the alert rule. Open `infra/prometheus/alerts.yml` and find `LatencyP95High`.

**Check:** you can say in one sentence what `> 0.2` and `for: 1m` mean.

**3.2** Start the load test in terminal B (1000 users for 1 minute):

```bash
make load
```

**3.3** Watch Prometheus: http://localhost:9090/alerts. Refresh every 15 seconds.

**Check:** `LatencyP95High` goes from `inactive` to `pending`, then to `firing` after about one minute above 200 ms. Note the time of each state.

**3.4** Watch the P95 panel in Grafana and the throughput panel.

**Check:** the P95 goes up, and the throughput goes up at the same time. Write both down.

**3.5** Follow the **Latency** section of `docs/runbooks.md`. Answer step 1 of the runbook: did throughput rise with the latency?

**Check:** you have a yes or no, with the number from step 3.4.

**3.6** Recover: stop the load (wait for the end of `make load`, or press `Ctrl+C`). Watch the P95 panel.

**Check:** P95 is back under 200 ms, and `LatencyP95High` goes back to `inactive` after a few minutes. Write down the decision time and the recovery time.

## Part 4 · Incident 2: a unit bug upstream

**4.1** Send the traffic with a unit bug (amounts multiplied by 100, as if sent in cents):

```bash
make simulate-unit-bug
```

**4.2** Wait 2 to 3 minutes, then check http://localhost:9090/alerts.

**Check:** `InputAmountShift` is `firing`. The alert does not say why.

**4.3** Compare the amounts in the logs. The last 500 lines of `logs/predictions.jsonl` are the incident traffic:

```bash
uv run python -c "import pandas as pd; d = pd.read_json('logs/predictions.jsonl', lines=True); d = d[d.event == 'prediction'].tail(500); print('median amount:', d.amount.median())"
```

**Check:** the median is in the thousands. Compare with the baseline of step 2.3.

Some requests may fail with `422` in terminal B (about 20 of 500). The schema accepts amounts up to 50 000 EUR, so amounts sent in cents above 500 EUR are rejected. A `422` is a client error, so it does not count as a 5xx in `ErrorRateHigh`: it is a clue in the logs, not an outage.

**4.4** Decide: are the amounts a real change of the population, or the same transactions expressed in cents? Write the evidence in one sentence.

**Check:** your sentence names one piece of evidence from step 4.3.

**4.5** Find the runbook action for this alert in the **Drift** section. Write down which action applies, and why retraining would be the wrong response here.

**Check:** your answer says the fix belongs at the source (the sender of the data), not in the model.

**4.6** Write one sentence on how you would fix the bug at the source and how you would check that the fix works.

**Check:** your sentence names a check you can run (for example: the median amount is back around 20 EUR after the fix).

**4.7** Restore normal traffic:

```bash
make simulate
```

**Check:** after a few minutes, `InputAmountShift` goes back to `inactive`.
